## Decisions

**Parchear la instalación, no bifurcar el harness.** `python3` en esta máquina es el stub
de la Microsoft Store y los hooks morían en silencio, pero `manifest.REQUIRED_HOOKS`
compara la cadena literal `python3 -m harness hook`, así que cambiar el intérprete deja el
`doctor` en *damaged*. Se descartó editar `harness/manifest.py`, porque el harness es
código del usuario y una bifurcación local se pierde en la siguiente copia. La salida fue
`tools/bin/python3`, un shim que reenvía a `python`, con los hooks anteponiendo ese
directorio al PATH: el comando sigue leyendo `python3 -m harness hook ...` y las dos
partes quedan contentas.

**`taskkill` sale de la lista deny.** En este repositorio cerrar los ejecutables en marcha
es parte del ciclo de build: mientras corren, el linker falla con LNK1168. El deny está
pensado para proteger trabajo sin commitear, y aquí bloqueaba el trabajo.

**El tablero no se deja vacío.** Un harness instalado y sin contenido no demuestra nada.
`sprint-001` arranca con las cinco tareas del performance harness escritas de verdad, y
`docs/ACTIVITY.md` con los seis frentes vivos.

**No se creó una tarea retroactiva para la instalación.** El trabajo está en tres commits
y en el WORK-LOG; una tarea inventada dentro de un sprint que empieza el 8 habría contado
una historia falsa. Lo que sí se escribió es lo que quedaba pendiente y se habría perdido:
TASK-0006 y TASK-0007.

**Ninguna referencia de git al harness.** El usuario lo pidió con estas palabras:
*"elimina la referencia de git del harness, no pushearemos nada al harness"*. Se borró el
clon temporal; el repositorio no tiene remotos, ni submódulo, ni `.git` anidado. El
harness queda vendorizado como archivos normales.
